# 이 글에서 다루는 내용
처음 참여한 해커톤에서 AI Workflow를 활용해 **CareBridge**라는 건강검진 결과 및 복약안내문 분석 서비스를 개발했다.

이 글에서는 아이디어를 선정하고 변경했던 이유부터 문서 분석 정확도 문제, Codex를 활용한 서비스 구현, 팀원들과의 협업, 데모데이까지의 과정을 정리했다.

## 1. 참여 계기

원래 여름방학 때 해커톤에 한번 참여해 보고 싶었다. 하지만 아직 개발 실력이 부족하다고 느꼈고, 괜히 팀에 민폐를 끼치는 건 아닐까 하는 걱정 때문에 선뜻 도전하지 못했다.

그러던 중 학기 중에 교내 사업단에서 진행하는 **AI Workflow Hackathon** 모집 공고를 보게 되었다. 마침 참가 대상이 1~2학년으로 제한되어 있었고, 나와 비슷한 수준의 학생들과 함께 프로젝트를 진행할 수 있을 것 같다는 생각에 바로 신청했다.

사실 모집 공고를 처음 봤을 때는 n8n이 무엇인지도 몰랐고, AI Workflow라는 개념도 생소했다. 단순히 AI를 활용해 무언가를 자동화하는 것인가 싶었지만, 오히려 어떤 기술인지 직접 경험해 보고 싶었다.

무엇보다 평소 AI를 자주 사용하면서도 직접 AI를 활용한 서비스를 만들어 본 경험은 없었다. 이런 프로젝트를 경험해 볼 기회가 흔치 않기도 하고, 이번 기회에 새로운 기술도 배우면서 직접 하나의 서비스를 만들어 보고 싶었다.

## 2. 팀 구성 및 아이디어 선정

### 2.1 팀 빌딩과 역할 선정

해커톤 참가 신청 당시 관심 분야와 사전 팀 구성 여부 등을 설문으로 제출했고, 이를 바탕으로 운영진이 팀 빌딩을 진행했다.

우리 팀은 같은 학과 학생 3명이 사전에 팀을 구성한 상태였고, 여기에 나와 다른 학생 한 명이 추가로 배정되어 총 5명으로 구성되었다.

팀 배정 이후 디스코드를 통해 간단히 자기소개를 나누고, 조장과 팀명을 정하는 시간을 가졌다.

그런데 조장을 정하는 과정이 조금 당황스러웠다. 기존에 팀을 구성했던 3명 중 대표 한 명과 새롭게 배정된 나를 포함한 2명, 총 3명만을 대상으로 랜덤 추첨을 진행한 것이다.

개인적으로는 5명 모두를 대상으로 정하는 것이 맞지 않나 싶어 의견을 이야기했지만, 결국 내가 조장으로 선정되었다. 조금 얼떨떨했지만 일단 선정된 만큼 조장을 맡기로 했다.

팀명은 남자 5명으로 구성된 팀이라는 점에서 착안해 내가 제안한 **FIVEGUYS**로 결정했다.

### 2.2 프로젝트 주제 선정

팀 구성이 마무리된 후에는 프로젝트 주제를 정하기 시작했다. 팀원들이 제안한 아이디어를 정리한 결과, 총 세 가지 후보가 나왔다.

| 후보 | 프로젝트 아이디어 |
|---|---|
| 1 | 건강검진 결과 해석 서비스 |
| 2 | 강의계획서 기반 학사일정 연동 서비스 |
| 3 | 제출 전 문서 요구사항 충족 여부 확인 서비스 |

투표 결과 1번과 3번이 동률이었고, 두 아이디어의 실현 가능성과 차별성을 비교해 보았다.

1번 건강검진 결과 해석 서비스는 기존 서비스와의 차별점을 만들기 어렵고, 의료 정보를 다루는 만큼 정확도에 대한 부담이 있다는 의견이 있었다.

반면 3번은 문서의 요구사항과 실제 제출물을 비교한다는 점에서 기능이 비교적 명확하고, 결과를 검증하기도 수월할 것이라고 판단했다.

무엇보다 당시가 10월 13일이었고, 바로 다음 날인 14일 오후 5시까지 미션 2를 제출해야 하는 상황이었다. 시간적 여유가 많지 않았기에 구현 가능성도 중요한 판단 기준이었다.

결국 내가 제안했던 3번 아이디어인 **SubmitShield**를 최종 주제로 선정하고, 팀원별 역할을 분담했다.

### 2.3 프로젝트 주제 재검토 및 변경

주제를 선정한 이후 서비스 기획서와 핵심 기능을 구체화하면서 SubmitShield에 대해 다시 생각해 보게 되었다.

SubmitShield는 과제 안내문과 제출물을 비교해 요구사항 충족 여부를 확인하는 서비스였다. 하지만 실제로 학생들이 이 서비스를 얼마나 필요로 할지 의문이 들었다.

이미 많은 학생이 생성형 AI를 활용해 과제를 작성하거나 검토하고 있었고, 별도의 서비스를 이용할 만큼 차별화된 가치를 제공하기 어려울 수도 있겠다는 생각이 들었다.

무엇보다 **우리가 만들려는 서비스가 실제로 사용자에게 필요한 서비스인지** 다시 고민하게 되었다.

그래서 처음에 후보로 논의했던 건강검진 결과 해석 서비스를 확장하는 방향을 팀원들에게 제안했다.

단순히 건강검진 결과를 해석하는 데 그치지 않고, 약국에서 제공하는 복약안내문까지 함께 분석해 실제 건강관리 행동으로 연결하는 서비스였다.

구체적으로는 다음과 같은 기능을 생각했다.

- **건강검진 결과 분석 :** 검사 수치와 참고범위를 추출해 사용자가 이해하기 쉽게 설명
- **복약안내문 분석 :** 약 이름, 복용 시점, 주의사항 등의 정보 추출
- **복약 일정 생성 :** 추출한 정보를 바탕으로 복약 일정표 자동 생성

이렇게 하면 단순한 문서 분석을 넘어 사용자의 일상적인 건강관리를 돕는 서비스로 발전시킬 수 있을 것 같았다.

또한 Upstage의 문서 분석 기능을 활용할 수 있고, 팀원들의 전공(디지털헬스케어공학과)과도 잘 맞는다는 점에서 충분히 시도해 볼 만하다고 생각했다.

다만 의료 정보를 다루는 만큼 AI가 임의로 진단하거나 복약 지시를 내리는 것은 제외하고, 문서에 기재된 정보를 정확하게 추출하고 정리하는 방향으로 범위를 제한했다.

아직 본격적인 개발을 시작하기 전이었기에 팀원들에게 이러한 생각과 함께 주제 변경을 제안했고, 최종적으로 건강검진 결과 및 복약안내문 분석 서비스인 **CareBridge**로 방향을 변경하게 되었다.

## 3. 프로젝트 개발 과정

### 3.1 CareBridge 서비스 소개

**CareBridge**는 건강검진 결과통보서와 약국 복약안내문을 분석해 사용자가 필요한 정보를 쉽게 확인하고 관리할 수 있도록 돕는 서비스다.

건강검진 결과통보서에는 검사 수치와 참고기준, 판정, 의학 용어 등이 여러 페이지에 나누어져 있다. 복약안내문 역시 약품마다 복용량과 횟수, 기간, 주의사항이 달라 사용자가 반복해서 확인해야 하는 불편함이 있다.

우리는 이러한 문서를 단순히 요약하는 데 그치지 않고, **필요한 정보를 추출하고 원문과 비교해 확인한 뒤 실제 관리로 연결하는 서비스**를 만들고자 했다.

주요 기능은 다음과 같다.

| 구분 | 주요 기능 |
|---|---|
| 문서 분석 | 건강검진 결과통보서 및 복약안내문 업로드 |
| AI 정보 추출 | 검사명, 수치, 참고기준, 약품명, 복약정보 등을 구조화 |
| 건강검진 정보 조회 | 주요 검사 결과와 용어 설명, 원문 참고기준 확인 |
| 복약정보 관리 | 약품별 복용량, 횟수, 기간 및 주의사항 확인 |
| 복약 일정 관리 | 사용자가 확인한 복약정보를 바탕으로 일정 등록 및 조회 |
| AI 해설 기능 | FactChat Gateway를 활용한 자연어 해설 생성 및 검증 기능(응답 안정화 미완료) |

**기술 스택**

- **Upstage Studio Agent:** Parse → Classify → Extract 기반 문서 분석
- **FactChat Gateway:** LLM API를 활용한 자연어 해설 생성 및 검증
- **Python:** 서비스 로직과 API 연동, 데이터 처리
- **Streamlit:** 웹 인터페이스 구현
- **Railway:** 웹 서비스 배포
- **Codex:** 코드 작성 및 개발 보조

다만 이번에 구현한 CareBridge는 해커톤용 프로토타입으로, 가상 문서를 중심으로 테스트했다. 사용자 계정 기반의 장기 기록 저장이나 자동 복약 알림 기능까지 완성하지는 못했다.

또한 AI가 사용자의 건강 상태를 직접 진단하거나 복용 방법을 결정하는 것이 아니라, 문서에 기재된 정보를 사용자가 이해하고 확인할 수 있도록 돕는 것을 목표로 했다.

### 3.2 AI Workflow 구성과 정확도 문제

최종 주제를 선정한 후, Upstage Studio를 활용해 문서 분석을 위한 AI Workflow를 구성했다.

AI Workflow는 여러 작업을 정해진 흐름에 따라 연결해 자동으로 처리하는 방식이다. 이번 프로젝트에서는 문서를 입력받아 필요한 정보를 추출하는 과정을 세 단계로 구성했다.

- **Parse :** 업로드한 문서에서 텍스트와 표 등의 구조를 인식하는 단계
- **Classify :** 입력된 문서가 건강검진 결과통보서인지 복약안내문인지 구분하는 단계
- **Extract :** 문서 유형에 따라 검사 수치, 약품명, 복용 방법 등 필요한 정보를 추출하는 단계

이렇게 추출한 정보를 이후 서비스에서 활용할 수 있도록 JSON 형태로 구조화했다.

예를 들어 복약안내문을 업로드하면 먼저 문서에 포함된 글자와 표를 읽고, 해당 문서를 복약안내문으로 분류한 뒤, 약품명과 복용 횟수 등의 정보를 정해진 항목에 맞춰 추출하는 방식이다.

하지만 실제 테스트 과정에서는 생각보다 많은 문제가 발생했다.

초기에는 예시 양식을 기반으로 가상 샘플 문서를 만들어 테스트했지만, 새로운 샘플에서는 Upstage Studio에 표시되는 정확도 점수가 50%대로 떨어지는 문제가 발생했다.

다만 화면에 표시된 점수만으로 실제 추출 정확도를 판단하기는 어려웠다. 실제로 일부 항목에서 추출 오류도 확인되어, 문서 분석 결과를 원문과 비교하며 더 자세히 점검할 필요가 있다고 생각했다.

팀원들과 원인을 논의하면서 특정 샘플의 구조에 추출 설정이 지나치게 맞춰진 것은 아닌지 의문이 들었다. 실제 건강검진 결과지나 복약안내문은 기관마다 형식과 정보 배치가 다를 수 있기 때문에, 다양한 문서에서도 안정적으로 정보를 추출할 수 있어야 한다고 생각했다.

그래서 추출 설명을 조금 더 일반화하는 방향을 제안했고, 추가적인 검증을 위해 LMS에서 제공한 `dummy-data-generator` 스킬을 활용했다.

이를 통해 건강검진 결과지 3종과 복약안내문 3종, 총 6종의 가상 PDF를 제작했다. 표형, 카드형, 서술형 등 서로 다른 형식으로 구성해 새로운 Agent에서 테스트한 결과, 모두 예상한 JSON 구조로 출력되는 것을 확인했다.

또한 실제 문서의 내용과 추출 결과를 비교하면서 검사 항목과 약품정보가 제대로 추출되었는지도 확인했다.

다만 JSON 구조가 정상적으로 출력된다고 해서 모든 정보가 정확하게 추출되었다는 의미는 아니었다. 테스트 과정에서도 일부 추출 오류가 발생했다.

팀에서는 별도로 합성 문서의 추출 결과를 정답과 대조하는 시험도 진행했다. 일부 시험에서는 높은 일치율을 확인했지만, 문서 구성과 Agent 설정, 평가 기준이 서로 달랐기 때문에 이를 하나의 정확도 수치로 정리하기는 어려웠다.

무엇보다 제한된 수의 가상 문서를 대상으로 진행한 테스트였기 때문에 실제 의료문서에서도 높은 정확도를 보장하기는 어려웠다. OCR 오류나 복잡한 문서 레이아웃에서 발생할 수 있는 문제는 여전히 추가적인 검증이 필요했다.

이번 테스트를 통해 비슷한 문서 분석 서비스를 개발한다면 처음부터 하나의 양식만으로 테스트하기보다는 서로 다른 구조의 문서를 준비하는 것이 중요하다고 생각했다.

또한 문제가 발생했을 때는 최종 결과만 수정하기보다 Parse 단계에서 문서 구조를 제대로 인식했는지부터 확인하고, 추출된 값이 원문과 일치하는지 검증하는 과정이 필요하겠다고 느꼈다.

이번 경험을 통해 **AI Workflow가 정상적으로 실행되는 것과 실제로 신뢰할 수 있는 결과를 제공하는 것은 별개의 문제**라는 점을 알게 되었다.

### 3.3 서비스 구현과 개발 방향의 차이

미션 2 제출 이후에는 팀원들이 Streamlit을 활용해 웹 서비스 데모를 구현하기 시작했다.

처음에는 준비된 샘플 PDF를 선택해 분석 결과를 확인하는 방식이었는데, 단순히 JSON 데이터를 보여주는 것보다 사용자가 이해하기 쉬운 설명을 제공한다는 점이 좋았다.

하지만 우리가 처음 기획했던 서비스와 비교하면 아쉬운 부분도 있었다.

사용자가 직접 문서를 업로드할 수 있어야 했고, 건강검진 결과와 복약정보를 단순히 보여주는 데 그치지 않고 지속적인 건강관리로 연결할 수 있어야 한다고 생각했다.

그래서 실제 문서 업로드, 핵심 요약, 복약 일정 관리 등의 기능을 제안했다.

이후 팀원들이 기능을 보완한 버전을 공유해 주었지만, 직접 테스트하면서 체크박스 선택 시 분석 결과가 초기화되는 오류와 문서 분석 안정성, AI 설명의 정확성 등 개선할 부분을 발견했다.

문제는 시간이 충분하지 않았다는 점이다.

최종 제출과 데모데이를 앞두고 있었지만, 팀원들의 시험 일정이 겹치면서 개발 진행 상황을 파악하고 일정을 조율하는 데 어려움이 있었다.

조장으로서 어떻게 프로젝트를 마무리해야 할지 고민이 많았다.

### 3.4 Codex를 활용한 CareBridge 재구현

결국 기존 기획서를 바탕으로 Codex를 활용해 별도의 CareBridge 서비스를 직접 구현해 보기로 했다.

서비스는 사용자가 Streamlit 웹 화면에서 건강검진 결과통보서나 복약안내문을 업로드하면, Upstage Studio Agent API를 통해 문서 유형을 분류하고 필요한 정보를 추출하는 방식으로 구성했다.

추출된 건강검진 결과는 검사명, 측정값, 참고기준과 원문 판정을 중심으로 정리하고, 주요 검사 용어에 대한 설명과 WHO 자료에 근거한 일반 생활습관 정보를 제공하도록 했다.

복약안내문의 경우에는 약품별 복용량과 횟수, 기간, 복용 시점, 주의사항을 추출해 원문 근거와 함께 확인할 수 있도록 구성했다.

특히 복약정보는 AI가 추출한 결과를 그대로 일정에 등록하는 것이 아니라, 사용자가 원문과 비교해 직접 확인한 정보만 일정으로 등록하도록 했다.

복용 횟수나 시점이 불분명한 경우에는 사용자가 다시 확인하도록 하는 방식이었다.

추가로 FactChat Gateway를 활용해 건강검진 결과에 대한 자연어 해설을 생성하는 기능도 구현했다.

하지만 이 과정에서도 문제가 있었다. 의료정보에 대해 AI가 근거 없는 설명이나 잘못된 판단을 생성하지 않도록 검증 조건을 강하게 설정했는데, 일부 문서에서는 정상적인 설명까지 차단되거나 생성에 실패하는 경우가 발생했다.

결국 최종 버전에서도 FactChat의 응답 안정성을 충분히 확보하지는 못했고, 해설 생성이나 검증에 실패하면 기본 안내를 제공하도록 구성했다.

또한 분석한 건강검진 결과와 복약정보를 조회하고, 사용자가 확인한 복약정보를 일정으로 등록하는 기능을 구현했다. 다만 기록은 주로 세션에서 관리하는 형태였으며, 사용자 계정을 통한 장기 저장이나 자동 복약 알림 기능까지 완성하지는 못했다.

서비스는 외부에서도 실행할 수 있도록 Railway에 배포했고, 실제 구현 코드는 GitHub에 정리했다.

물론 Codex를 활용했다고 해서 모든 문제가 자동으로 해결된 것은 아니었다. 실제로 서비스를 실행하고 테스트하면서 오류를 수정하고, AI가 추출한 값이 원문과 일치하는지 확인하고, 기획했던 기능이 의도대로 동작하는지 계속 확인해야 했다.

이후 두 버전을 각각 개발하기보다는 내가 구현한 버전을 기반으로 통합하는 것이 효율적이라고 판단해 팀원들에게 제안했다.

당시에는 새로운 기능을 계속 추가하는 것보다 **하나의 버전으로 통합하고, 남은 시간 동안 안정성과 완성도를 높이는 것**이 더 중요하다고 생각했다.

### 3.5 오피스아워와 기술적 피드백

10월 16일에는 오피스아워에 참석해 개발 과정에서 고민했던 문제들을 멘토님께 질문했다.

가장 궁금했던 부분은 문서 정보 추출의 정확도와 AI가 잘못된 의료정보를 생성할 가능성이었다.

문서 추출 오류에 대해서는 먼저 Parse 단계의 결과를 확인하고, 문제가 없다면 Extract 단계의 설정과 추출 결과를 점검하라는 조언을 받았다. 또한 필드별 예외 처리와 2단계 검증을 통해 잘못된 정보가 그대로 사용되지 않도록 하는 방법도 알게 되었다.

AI가 생성하는 설명에 대해서는 의료적 진단이나 처방을 대신하지 않는다는 안내가 필요하고, 복약정보를 임의로 변경하지 못하도록 가드레일을 설정해야 한다는 피드백을 받았다.

특히 Parse 단계에서부터 잘못 추출된 정보가 이후 Extract와 LLM 설명 생성 단계까지 전달될 수 있다는 점에서, 단순히 최종 출력만 확인하기보다 각 단계의 결과를 개별적으로 검증하는 것이 중요하다고 이해했다.

또한 의료정보를 다루는 서비스에서는 자연스러운 AI 설명을 생성하는 것만큼, 원문에 없는 정보를 추가하거나 잘못된 복약정보를 제공하지 않도록 제한하는 과정도 필요하다는 생각이 들었다.

멘토링 이후에는 질문과 답변을 정리해 팀원들에게 공유했고, 남은 개발 시간과 구현 가능성을 고려해 적용할 부분을 검토했다.

이와 함께 개인정보 보호 문제도 고려해야 했다.

건강검진 결과와 복약안내문에는 개인의 건강정보가 포함될 수 있고, 문서를 분석하기 위해 외부 AI 서비스로 정보를 전송해야 한다는 점에서 주의가 필요했다.

서비스에서는 문서 전송 전에 사용자 동의를 받도록 구성했다. 또한 추가적인 AI 해설 과정에서는 원본 문서 전체나 직접 식별정보가 불필요하게 전달되지 않도록 하는 방향을 고려했다.

다만 완전한 비식별화나 실제 의료서비스 수준의 보안성까지 확보한 것은 아니었다.

이번 경험을 통해 **AI 서비스를 개발할 때는 기능이 정상적으로 동작하는지만 볼 것이 아니라, 결과의 정확성과 안전성, 데이터가 처리되는 과정까지 함께 고려해야 한다는 점**을 생각하게 되었다.

### 3.6 최종 개발과 서비스의 차별성 고민

개발을 마무리하면서 또 다른 고민이 생겼다.

**과연 사용자가 CareBridge를 이용해야 할 이유가 충분할까?**

처음에는 건강검진 결과와 복약안내문을 분석하고 설명하는 기능에 집중했지만, 단순히 문서를 요약하는 것만으로는 일반적인 생성형 AI와 차별화하기 어렵다고 느꼈다.

실제로 가상 건강검진 결과통보서를 살펴보니 결과지 자체에 종합 소견과 생활습관 관리 방법이 이미 포함되어 있었다. 

그렇다면 AI가 이를 다시 요약하고 설명하는 것만으로 사용자에게 얼마나 큰 가치를 줄 수 있을지 의문이 들었다.

물론 여러 페이지에 흩어진 검사 수치와 용어를 한눈에 확인할 수 있다는 장점은 있었다. 하지만 단순히 정보를 정리해서 보여주는 것만으로 사용자가 계속 이용할 만한 서비스가 될 수 있을지는 확신이 없었다.

그래서 복약안내문에서 추출한 정보를 실제 일정 관리와 알림 기능으로 연결하는 방향을 생각했다. 

여러 약을 복용하는 사용자가 일일이 약 이름과 복용 시간을 확인하는 부담을 줄이고, 단순한 정보 제공을 넘어 일상적인 건강관리에 도움을 주고 싶었다.

특히 의료정보를 다루는 만큼 AI가 추출한 결과를 그대로 믿고 사용하는 것은 위험할 수 있었다. 그래서 불분명한 정보는 임의로 확정하지 않고, 사용자가 원문과 대조해 확인한 정보만 일정에 등록하도록 구성했다.

결국 우리가 생각한 CareBridge의 차별점은 AI가 의료문서를 읽고 설명하는 기능 자체보다는, **문서에서 필요한 정보를 추출하고, 사용자가 직접 확인한 뒤, 이를 일상적인 관리로 연결하는 과정**에 있었다.

여기에 자동 알림 기능까지 구현할 수 있다면 복약 일정을 놓치지 않도록 돕는 서비스로 발전시킬 수 있을 것이라고 생각했다.

하지만 개발 기간이 짧아 알림 기능을 완성하지는 못했고, 실제 사용자가 얼마나 편리하게 활용할 수 있을지도 충분히 검증하지 못했다.

또한 기존 서비스나 범용 AI보다 CareBridge가 더 뛰어나다는 점을 객관적으로 입증한 것도 아니었다.

남은 시간이 많지 않았기 때문에 새로운 기능을 무리하게 추가하기보다는 기존에 구현한 문서 분석과 사용자 확인, 일정 등록 기능의 안정성을 높이는 방향으로 마무리하기로 했다.

돌이켜보면 처음 주제를 선정할 때도 서비스의 필요성과 차별성을 고민했지만, 실제 개발 과정에서는 구현할 기능과 기술적인 문제에 더 집중했던 것 같다.

그러다 개발을 마무리할 무렵 다시 사용자의 입장에서 생각해 보니, 우리가 만든 기능이 실제로 얼마나 필요한지 충분히 검증하지 못했다는 아쉬움이 남았다.

이번 경험을 통해 **기술적으로 구현할 수 있는 기능과 사용자가 실제로 필요로 하는 기능은 다를 수 있다**는 점을 생각하게 되었다.

다음에 비슷한 프로젝트를 진행한다면 실제 사용자의 불편함과 기존 해결 방법을 더 구체적으로 살펴보고, 우리가 제공할 수 있는 가치를 먼저 명확하게 정의해 보고 싶다.

## 4. 최종 제출과 데모데이

### 4.1 마지막까지 이어진 협업의 어려움

최종 제출을 앞두고 개발뿐만 아니라 발표자료, 시연 영상, 발표 대본, 질의응답까지 준비해야 했다.

하지만 개발 방향이 여러 차례 변경되면서 초기에 정했던 역할과 실제 필요한 업무가 달라졌고, 팀원들의 시험 일정까지 겹쳐 역할을 조율하는 데 어려움이 있었다.

나 역시 서비스 개발과 오류 수정에 많은 시간을 쓰고 있었기 때문에 발표 준비까지 모두 담당하기는 어려운 상황이었다.

그래서 남은 업무를 다시 정리하고 팀원들에게 역할 분담을 요청했지만, 기존에 정했던 역할에 대한 이해가 서로 달라 의견 차이가 생겼다.

당시에는 솔직히 답답하고 부담스럽기도 했다. 다만 돌이켜 보면 **주제와 개발 방향이 바뀌는 과정에서 역할과 책임을 명확하게 다시 정하지 못한 점**도 문제였던 것 같다.

이후 팀원들과 다시 이야기하면서 발표자료와 시연 영상, 발표, 질의응답 등의 업무를 정리했고, 최종 데모데이를 준비할 수 있었다.

현장에서는 최종 발표를 준비하고, 각 팀의 프로젝트를 전시하며 동료평가와 심사에 참여했다.

이후 CareBridge의 문제 정의, 핵심 기능, 기술 구조와 시연 내용을 발표하고 질의응답을 진행했다.

동료평가와 프로젝트 전시를 진행하면서 다른 참가자들에게 CareBridge를 설명할 기회도 있었다. 이 과정에서 우리가 기획한 서비스가 실제로 어떤 상황에서 활용될 수 있을지 조금 더 구체적으로 생각하게 되었다.

특히 나이가 들면서 여러 질환으로 복용하는 약이 늘어나는 경우, 복약 일정과 약의 종류를 일일이 관리하기 어려울 수 있겠다는 생각이 들었다. 보호자가 복약안내문을 등록하고 일정을 관리할 수 있다면 사용자에게 도움이 되지 않을까 싶었다.

처음에는 문서를 분석하고 일정을 생성하는 기능에 집중했지만, 다른 사람들에게 서비스를 설명하면서 실제 사용자의 입장에서 기획 의도를 다시 생각해 볼 수 있었다.

발표는 팀원이 맡아 진행했고, 나는 기술적인 내용과 서비스 구현 과정에 관한 질문에 답변했다.

### 4.4 데모데이 이후 개선 방향

데모데이에서 다른 팀들의 프로젝트를 살펴보면서 CareBridge를 어떻게 발전시킬 수 있을지 생각해 볼 수 있었다.

특히 러닝플로우 팀의 **medicineat**이라는 프로젝트가 기억에 남았다. 일반의약품의 사진을 분석해 제품명을 확인하고, 공식 의약품 정보를 바탕으로 여러 약에 동일한 성분이 포함되어 있는지 비교하는 서비스였다.

CareBridge를 개발하면서도 서로 다른 날짜에 처방받은 약이나 여러 약품의 성분이 겹치는지 확인하는 기능을 생각했었는데, medicineat의 구현 방식을 보면서 두 서비스의 기능을 결합하면 어떨까 하는 생각이 들었다.

CareBridge가 건강검진 결과와 복약안내문을 분석해 복약 일정과 이력을 관리하고, 여기에 일반의약품의 성분을 비교하는 기능까지 추가한다면 사용자가 자신의 복약정보를 조금 더 편리하게 관리할 수 있을 것 같았다.

또한 과거부터 현재까지 복용했던 약과 건강검진 결과를 하나의 포트폴리오처럼 관리하는 방향도 생각해 보았다. 사용자가 자신의 건강정보를 돌아보거나 병원 진료 시 현재 복용 중인 약과 과거 복약 이력을 쉽게 확인할 수 있다면 유용하지 않을까 싶었다.

하지만 이러한 기능을 구상하면서 한계도 발견했다. 복용했던 약만으로 과거의 질환을 정확하게 판단하기 어렵고, AI가 이를 잘못 해석해 부정확한 생활 가이드를 제공할 가능성도 있었다. 또한 의료기관에서는 이미 진료기록과 처방정보를 관리하는 시스템을 사용하고 있어, 기존 시스템과 어떤 차별점을 가질 수 있을지도 고민해야 했다.

특히 약품의 동일 성분을 확인하는 것과 실제 병용 안전성을 판단하는 것은 다른 문제이기 때문에, 단순히 AI가 안전 여부를 판단하도록 해서는 안 된다고 생각했다.

결국 CareBridge가 발전해야 할 방향은 AI가 사용자의 건강 상태를 직접 판단하는 것이 아니라, **기존 의료문서를 사용자가 더 쉽게 이해하고, 복약 일정과 건강기록을 일상에서 관리할 수 있도록 돕는 것**이라고 생각했다.

이를 바탕으로 앞으로 개선해 보고 싶은 부분을 정리했다.

**① 문서 분석 정확도 및 사용자 검증**

- 다양한 시기의 복약안내문과 건강검진 결과통보서를 활용해 문서 추출 성능 검증
- OCR 오류나 수기 문서 등 다양한 입력 조건에 대한 테스트
- 추출된 정보를 사용자가 직접 확인하고 수정한 후 저장하는 검증 단계 추가

**② 건강정보 통합 관리**

- 여러 건강검진 결과지와 복약안내문을 업로드하고 비교하는 기능
- 사용자별 계정을 통한 건강정보 포트폴리오 관리
- 과거부터 현재까지 건강검진 수치와 복약정보의 변화 확인

**③ 복약 관리 기능 고도화**

- 서로 다른 날짜에 처방받은 약과 일반의약품의 동일 성분 중복 여부 확인 기능 검토
- 공식 의약품 정보 연동 및 추출된 약품정보의 사용자 확인 과정 추가
- 보호자와 함께하는 복약 일정 관리 및 알림 기능 개선

**④ AI 서비스의 활용성 및 차별화**

- Solar Pro 등을 활용한 대화형 AI 기능 검토
- 사용자가 자신의 건강정보에 대해 직접 질문할 수 있는 인터페이스 구상
- 일반적인 LLM 서비스와 비교했을 때 CareBridge만의 차별성 검토
- 건강정보 포트폴리오의 실제 활용 상황과 기존 의료정보 시스템과의 차별성 검토

다만 이러한 기능을 추가하는 것만으로 좋은 서비스가 되는 것은 아닐 것이다. 실제 사용자에게 필요한 기능인지, 의료정보를 안전하고 정확하게 처리할 수 있는지 충분한 검증이 필요하다고 생각한다.

## 5. 활동 회고

이번 해커톤은 여러모로 많은 것을 느끼게 해준 경험이었다.

처음에는 개발 실력이 부족하다는 걱정 때문에 참여를 망설였지만, 막상 참여하고 나니 예상치 못하게 조장을 맡게 되었고, 주제 선정부터 서비스 개발, 최종 발표까지 생각보다 많은 일들을 경험하게 되었다.

가장 힘들었던 부분은 팀원들과의 협업이었다.

해커톤 일정이 시험기간과 겹치다 보니 나 역시 시험공부와 프로젝트를 병행해야 했다. 그렇다고 기왕 참여한 프로젝트를 대충 마무리하고 싶지는 않았고, 어느 정도 완성도 있는 결과물을 만들고 싶었다.

하지만 개발이 생각처럼 진행되지 않았고, 팀원들과 역할을 나누었음에도 진행 상황을 공유하거나 함께 문제를 해결하는 과정이 원활하지 않았다. 그러다 보니 점점 팀 프로젝트보다는 혼자 프로젝트를 진행하는 듯한 느낌이 들었고, 그만큼 부담과 스트레스도 커졌던 것 같다.

솔직히 당시에는 많이 답답하고 속상했다. 팀원들마다 개발 역량과 참여할 수 있는 시간이 다르다는 점은 이해했지만, 적어도 서로의 진행 상황을 공유하고 함께 해결하려는 노력이 필요하다고 생각했기 때문이다.

그렇다고 나 역시 조장으로서 잘했다고 생각하지는 않는다.

돌이켜 보면 프로젝트 초반에 팀원들과 충분히 소통하면서 각자의 상황과 역량을 파악하고, 역할과 일정을 조금 더 명확하게 정했어야 했던 것 같다.

특히 시험기간과 겹친 짧은 일정, 온라인 중심의 활동이라는 점도 협업이 원활하지 않았던 이유 중 하나였을 수 있다. 가능했다면 초반에 오프라인으로 만나거나 온라인 회의를 통해 서로의 생각과 목표를 맞춰보는 시간을 가졌으면 어땠을까 하는 아쉬움도 남는다.

또한 진행 상황이 공유되지 않거나 일정이 지연될 때, 조장으로서 조금 더 일찍 단호하게 이야기했어야 했다는 생각도 든다. 팀원들의 상황을 고려하는 것도 중요하지만, 프로젝트를 완성하기 위해 필요한 책임과 기준을 명확하게 전달하는 것 역시 중요하다는 것을 느꼈다.

물론 그렇게 한다고 해서 모든 팀원이 적극적으로 참여하는 것은 아닐 것이다. 사람마다 생각과 태도가 다르고, 조장이라고 해서 모든 상황을 통제할 수 있는 것도 아니니까.

결국 **여러 사람의 상황을 고려하면서도 공동의 목표를 향해 함께 움직이도록 만드는 것이 생각보다 훨씬 어려운 일**이라는 것을 느꼈다.

기술적인 부분에서도 아쉬움이 남는다.

AI를 활용해 서비스를 구현하고 배포할 수 있었지만, 다른 팀들의 결과물을 보면서 같은 AI 도구를 사용하더라도 결과물의 완성도는 크게 달라질 수 있다는 점을 느꼈다.

나 역시 여러 기능을 구현하고 문제를 해결하려고 했지만, 이것저것 동시에 진행하다 보니 하나의 문제에 충분히 집중하지 못했던 것 같다.

조금 더 시간을 들여 서비스의 필요성과 구조를 고민하고, 핵심 기능부터 차근차근 구현했다면 더 좋은 결과물을 만들 수 있지 않았을까 하는 아쉬움도 남는다.

그럼에도 긍정적으로 생각하는 부분은 있다.

처음에는 해커톤에 참여하는 것조차 망설였지만, 결국 직접 아이디어를 제안하고, AI를 활용해 서비스를 구현하고 배포하는 경험까지 해볼 수 있었다.

무엇보다 여러 어려움이 있었음에도 **끝까지 포기하지 않고 프로젝트를 마무리하려고 노력했다는 점**은 스스로 좋게 평가하고 싶다.

완성도와 협업 과정 모두 아쉬움이 남지만, 이번 경험을 통해 내가 어떤 부분에서 부족한지 조금 더 구체적으로 알게 된 것 같다.

다음에 프로젝트를 진행한다면 문제 정의와 서비스 설계에 충분한 시간을 투자하고, 팀원들과 역할과 일정을 명확하게 공유하면서 함께 하나의 결과물을 완성해 나가고 싶다.

쉽지만은 않았던 첫 해커톤이지만, 그래서 더 많은 것을 배우고 느낄 수 있었던 경험이었다.
